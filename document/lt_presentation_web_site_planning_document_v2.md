# 「メディアアートとは？」LT用インタラクティブWebスライド 企画書 (v2)

## 1. プロジェクト概要
* **発表テーマ**: メディアアートとは？
* **目的**: LT会の発表資料(スライド代わり)。メディアアートという題材そのものを、Webスライドの演出(Three.js / p5.js)で体感させ、メッセージを印象づける。
* **ターゲット**: LT会の聴講者(20代のエンジニア・クリエイター層)。視覚的新しさとテンポの良さを好む層。
* **コア体験**: 静的なスライドの枠を超えた、ミニマルな世界観とリッチなインタラクションの「体験型プレゼンテーション」。サイト自体が小さなメディアアート作品として機能することを狙う。
* **成功の定義(案)**: 発表後、聴講者が「メディアアートとは何か」を自分の言葉で一言説明でき、気になる作品を1つ以上挙げられ、「自分も作ってみよう」と思える。

## 2. 発表構成
草案: `ref/発表構成 4002d534ad248040b628c236a3a81315.md`。セクション区切りは `---`。持ち時間は約30分。

### 2.1 ページ構成
発表は「index(縦スクロールのLP)」と「別ページ2つ(スライドシステム)」の3ページで構成する。indexの流れの途中で2回、別ページへ遷移し、終わったらindexの続きへ戻る。

| ページ | URL | 形式 | 内容 |
|---|---|---|---|
| index | `/` | スクロール連動LP(セクション単位) | タイトル、アートの定義、まとめ、メディアアートの世界(導入)、作り方 |
| chapter1 | `/chapter1` | **スライドシステム** | 「デザイン」「エンタメ」「アート」の区別 |
| chapter2 | `/chapter2` | **スライドシステム** | メディアアート作品の紹介 |

### 2.2 indexのセクション(`---` 区切り)
| # | セクション | 内容 |
|---|---|---|
| 1 | タイトル | 「メディアアートとは？」 |
| 2 | アートとは何か | 暫定的な定義文と出典(museumstudies.jp)。結論は「つまり、アートが何かは分かっていない。~完~」 |
| 3 | ここからは偏見になります | 「デザイン」「エンタメ」「アート」の区別とは？ → **chapter1へ遷移** |
| 4 | アートとは | 「アートは自分の感情を形にするもの」。動機は「面白い」「カッコイイ」「楽しんでほしい」で十分 |
| 5 | メディアアートの世界 | 「メディア」=PC・スマホ・センサ等のIT機器。どんな作品があるか → **chapter2へ遷移** |
| 6 | 作品に触れてアイデアを蓄えよう | chapter2から戻った後のまとめ |
| 7 | メディアアートの作り方 | 1.やりたいことを言語化 2.手段を選ぶ 3.作って壊してみる |

* 遷移はクリックまたはキー操作で行い、発表者が意図したタイミングでのみ起こす(誤スクロールで遷移しない)。
* chapter1/2を終えたら、**遷移元の次のセクションへ戻る**(例: chapter1終了 → index セクション4)。ブラウザの戻る操作でなく、アプリ内で位置を指定して戻す。
* セクション2の定義文は長文なので、スライド表示用に分割/要約し、出典は小さく残す。

## 3. 当日の運用条件(要件を左右する前提)
* **発表者のPCからローカル(オフライン)のサイトにアクセスし、会場の有線接続(HDMI等)でプロジェクター/ディスプレイへ出力して発表する。**
* 画面共有ツールは使わないため、共有機能はシステムに組み込まない。
* これにより次を設計上の前提とする。
  * **完全オフライン動作**: 外部通信に一切依存しない。YouTube埋め込み・外部CDN・Webフォント配信は使わない。
  * **投影環境での見え方**: プロジェクターは明るい会場で暗部が潰れ、色も浅くなる。細かい粒子、微細なグラデーション、低コントラストは避け、大きく、太く、高コントラストにする。
  * **出力設定**: 解像度・アスペクト比は会場機材で決まる(16:9とは限らない)。縮尺スケーリングは、16:9固定+レターボックスで、4:3出力でも崩れないようにする。ミラーリングか拡張ディスプレイかは当日の接続で確認する。
  * **音声**: 動画に音声を使う場合は、HDMIで会場スピーカーに出せるか事前確認する。出せない場合は無音前提で作る。
  * **発表者の画面操作**: 拡張ディスプレイ利用時は、発表者ビュー(タイマー・ノート)を手元側の別ウィンドウに出せると望ましい(任意要件)。
  * **スリープ防止**: 発表中に画面が消えないよう、Wake Lock API等を使う。

## 4. デザイン・トーン&マナー
* **参考**: ペンギン・キャピタル(https://www.penguin-capital.co.jp/ja)の雰囲気。デザイン・文言・アセットは流用せず、あくまで参考にとどめる。
* **トーン**: ミニマル、重厚感、洗練されたタイポグラフィ、ダークモード基調。
* **カラー**: 黒・チャコールをベースに、白と鋭いアクセントカラー1〜2色。
* **世界観**: スクロールやキー操作に連動して空間がなめらかに変化する没入感。
* **可読性基準(投影向け)**: 本文は最小でも画面高の約4%以上のサイズ、コントラスト比は4.5:1以上。1スライド1メッセージ。

## 5. システムアーキテクチャ & 技術スタック
* **構成**: DBレス・フロントエンド完結のSPA。**Vite + React + TypeScript + React Router**に確定。
* **配布方法**: `vite build` の成果物を発表PCにローカル保持し、ローカルサーバーで配信(例: `vite preview` または静的サーバー)。`file://` 直開きはルーティングやアセット読み込みで問題が出やすいため避ける。
  * 保険としてCloudflare Pages等にも同じビルドを置いてよいが、当日はオフライン版を使う。その場合、SPAフォールバック設定(`_redirects` / rewrites)を入れる。
* **スタイリング**: Tailwind CSS(バージョンを固定。v4なら `tailwind.config.js` は原則不要)。
* **3D / グラフィックス**: Three.js(React Three Fiber採用可)、p5.js(インスタンスモード)。
  * アンマウント時に必ずリソース解放(Three.jsは `dispose`、p5は `remove()`)する共通ラッパーを作る。
  * ページ単位でlazy loadし、初期バンドルを抑える。
* **アニメーション/スクロール**: GSAP、Lenis等から選定(要決定)。
* **コードブロック**: Shiki等(ビルド時ハイライトでオフライン対応)。※メディアアート紹介では出番が少なければ縮小可。
* **フォント**: 日本語・英字とも自己ホスト(`@fontsource` 等でバンドル)。サブセット化で容量を抑える。
* **動画**: すべてローカルファイル(`public/videos`)。YouTube埋め込みは**採用しない**。

## 7. 主要機能要件
1. **indexページ(縦スクロールLP)**
   * セクション単位(`---` 区切り)で表示し、スクロールまたはキー操作で進む。背景のThree.jsやテキストがセクションに連動して変化する。
   * 2箇所(セクション3・5)に、chapter1・chapter2へ遷移する導線を置く。
   * chapter終了後は、遷移元の次のセクションに復帰する(URLのハッシュ等で位置を保持)。
2. **章ごとのスライドページ**
   * URLが章ごとに独立(`/chapter1`、`/chapter2`)。スライドシステムの対象はこの2ページ。
   * 進行操作: 左右矢印、スペース、**PageUp / PageDown(クリッカー対応)**、画面クリック。
   * 最後のスライドの次の操作で、indexの続きへ戻る。最初のスライドで戻る操作をした場合は、遷移元のindexセクションへ戻る。
   * 進行状況インジケーター(章・枚数)を控えめに表示。
   * 16:9固定のスケーリング、フルスクリーン(Fキー)。
3. **スライド定義方式**
   * `src/slides/` にデータ(または小コンポーネント)として1枚ずつ定義。テンプレート種別(タイトル / 比較・区別 / 作品紹介)を用意し、入力の手間を減らす。
   * ステップ表示(クリックごとに要素を出す)に対応。
4. **作品紹介コンポーネント**
   * 作品名・作者・年・画像/動画・一言解説を表示。クレジットは必ず入れる。
5. **リッチ表現**
   * Three.js / p5.jsによるインタラクティブな演出(定義の説明、切り口の可視化など)。
6. **軽量モード**
   * 負荷が高い場合に演出を落とす切替(例: Qキー)。投影時の負荷対策。

## 8. 非機能要件
* 対応ブラウザ: 発表PCのブラウザ(Chrome最新版を想定。要確認)。
* 性能: 発表PCで体感60fps、最低でも30fps。
* オフライン: ネットワークを切断した状態で全機能が動作すること。
* アクセシビリティ: `prefers-reduced-motion` を尊重(ただし発表用に手動で演出ONへ切替可)。
* 容量: 動画・3Dモデルは圧縮し、読み込み待ちが出ないよう主要アセットをプリロード。
